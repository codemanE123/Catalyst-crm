# Data Privacy and University-Readiness Audit

Scope: Documentation-only audit of current CRM data handling, classification, privacy protections, retention, access controls, audit logging, and deletion/export readiness.

## Executive summary

The app currently handles data that ranges from public institutional data to restricted CRM intelligence. Public university profile data is generally low sensitivity, but contacts, interview notes, budget discussions, objections, pipeline status, and AI-generated summaries require strong access controls. The current app does not yet implement authentication, authorization, tenant boundaries, audit logs, retention controls, export workflows, or deletion workflows. It is not ready for real university/customer data without these controls.

## Data classification model

### Public

Definition: Information intentionally available to the public or collected from public university websites.

Examples:

- School name.
- Public school website.
- State.
- Public/private designation when public.
- Public HBCU/community-college status.
- Public enrollment figures.
- Public AI, cyber, healthcare program pages.
- Public innovation/entrepreneurship/career/workforce office references.
- Source URLs.

Controls:

- Can be displayed to authenticated CRM users.
- Still should include provenance/source URLs.
- Should not be treated as verified unless reviewed.

### Internal

Definition: Operational CRM metadata generated by the organization.

Examples:

- CRM owner.
- Pipeline status.
- Next step.
- Outreach dates.
- Follow-up status.
- CEO metrics and pipeline counts.
- Research-agent preview/save status.

Controls:

- Organization-scoped access.
- Visible to Sales, Admin, Super Admin, and possibly Read Only.
- Audit changes to status and ownership.

### Confidential

Definition: Business-sensitive relationship and engagement data.

Examples:

- Contact names.
- Contact roles.
- Contact emails.
- Contact phone numbers.
- Contact relationship status.
- Outreach subject/message/outcome.
- Contact notes.
- School account notes.
- Interview summaries.
- Referrals.
- Current tools.
- Pilot interest/readiness.

Controls:

- Authenticated and organization-scoped only.
- Role-based access.
- Read Only may view limited fields depending on policy.
- Exports should be logged.
- Deletion requests must include these records.

### Restricted

Definition: Sensitive commercial, strategic, or personally identifiable context that could create harm if exposed.

Examples:

- Raw interview notes.
- Pain points.
- Buyer.
- Budget.
- Budget owner.
- Pricing/funding discussions.
- Objections.
- AI-generated summaries derived from interview notes.
- Follow-up notes involving deal strategy.
- Any notes containing student-level data, even if accidental.

Controls:

- Strict least-privilege access.
- Field-level redaction for Read Only users.
- Strong audit logging for reads/exports/updates.
- Retention limits.
- Deletion/export workflows.
- Avoid sending to third-party AI services without a DPA and explicit policy.

## Current protection assessment

| Data area | Current classification | Protected today? | Notes |
| --- | --- | --- | --- |
| Contact information | Confidential | No | Stored/displayed without app auth or role checks. |
| Interview notes | Restricted | No | Raw notes, summaries, pain points, buyer/budget/objections are available through profile views. |
| Pricing/budget discussions | Restricted | No | `budget`, `budget_owner`, and related notes have no field-level access control. |
| School pipeline status | Internal | No | Pipeline/status fields are visible to any app visitor in a deployed environment. |
| User accounts | Restricted | Not implemented | No user account model exists yet. |
| AI-generated summaries | Restricted | No | Stored as interview fields and rendered in profiles without auth/role gates. |
| Public university research | Public/Internal | Partially | Public source data is lower risk, but saved CRM interpretation should be org-scoped. |

## Contact information

Current data:

- `contacts.name`
- `contacts.role`
- `contacts.email`
- `contacts.phone`
- `contacts.relationship`
- `contacts.notes`

Current risk:

- Contact details render on dashboard/profile pages.
- No authentication or authorization.
- No role-based field redaction.
- No export/deletion workflow.

Recommendations:

- Classify contact information as Confidential.
- Require authenticated organization membership.
- Limit Read Only users to name/title/school unless explicitly allowed.
- Log exports containing contact information.
- Add contact deletion and correction workflows.
- Add data source/provenance for imported contacts.

## Interview notes

Current data:

- `interviews.notes`
- `interviews.raw_notes`
- `interviews.pain_points`
- `interviews.current_tools`
- `interviews.buyer`
- `interviews.budget`
- `interviews.budget_owner`
- `interviews.objections`
- `interviews.referrals`
- `interviews.next_step`

Current risk:

- Notes can contain sensitive commercial context or accidentally include student/person-level information.
- AI-generated summaries preserve and restructure sensitive details.
- No retention policy.
- No access or export audit trail.

Recommendations:

- Classify raw interview notes and AI summaries as Restricted.
- Add retention policy for raw notes.
- Consider storing raw notes separately from derived summaries.
- Redact raw notes from Read Only users.
- Add field-level audit logs for reads/updates/exports.
- Add warning UI: do not enter student PII or protected education records.

## Pricing discussions

Current data:

- `interviews.budget`
- `interviews.budget_owner`
- budget references inside `raw_notes`, `notes`, `objections`, and `next_step`

Current risk:

- Budget owner and pricing context can reveal procurement strategy and commercial sensitivity.
- No role boundaries separate sales users from viewers.

Recommendations:

- Classify pricing/budget discussions as Restricted.
- Only Sales, Admin, and Super Admin should see/edit pricing fields.
- Read Only should see redacted or aggregated deal status.
- Audit all changes to budget/pricing fields.
- Consider splitting pricing fields into a dedicated restricted table.

## School pipeline status

Current data:

- `schools.status`
- `schools.next_step`
- `follow_ups.status`
- `follow_ups.due_date`
- CEO pipeline metrics

Current risk:

- Pipeline data is internal business intelligence.
- No organization scoping or role checks.

Recommendations:

- Classify pipeline status as Internal.
- Restrict to authenticated organization users.
- Allow Read Only to view pipeline summaries but not sensitive follow-up notes.
- Audit changes to `status`, `next_step`, and follow-up completion.

## User accounts

Current state:

- No application user accounts.
- No organization membership.
- No role storage.
- No user profile table.

Current risk:

- The app cannot enforce privacy rules without users and roles.

Recommendations:

- Add Supabase Auth.
- Add `organizations`.
- Add `organization_members`.
- Add role enum: `super_admin`, `admin`, `sales`, `read_only`.
- Add ownership fields to all CRM records.
- Log user ID on every write.

## AI-generated summaries

Current behavior:

- Summary helper runs client-side with heuristics.
- It turns raw notes into structured fields.
- Data can be submitted into `interviews`.

Current risk:

- AI summaries can amplify sensitive information by making it easier to find, export, or misuse.
- There is no confidence score, review status, or provenance.
- There is no policy preventing protected student information from being pasted into raw notes.

Recommendations:

- Classify AI summaries as Restricted when derived from interview notes.
- Store `ai_summary_reviewed_by`, `ai_summary_reviewed_at`, and `ai_summary_confidence` if summaries are used operationally.
- Add UI copy requiring human review.
- Add data minimization guidance.
- If using external AI later, require vendor DPA, retention controls, and no-training guarantees.

## Data retention recommendations

Suggested defaults:

| Data type | Retention | Recommendation |
| --- | --- | --- |
| Public university research | 12-24 months | Refresh periodically; keep sources and crawl date. |
| Contact info | Active relationship + 24 months | Delete/anonymize stale contacts after inactivity. |
| Outreach history | 36 months | Retain for business context; archive after retention window. |
| Interview summaries | 24-36 months | Retain while opportunity is active; archive/delete after inactivity. |
| Raw interview notes | 12 months | Shorter retention because raw notes are highest risk. |
| Budget/pricing fields | Active deal + 24 months | Restrict and audit; delete when no longer needed. |
| Follow-ups | 24 months after completion | Keep active follow-ups; archive completed ones. |
| Audit logs | 3-7 years | Retain longer for compliance/security investigations. |

Implementation recommendations:

- Add `archived_at`, `deleted_at`, and `retention_expires_at`.
- Prefer soft delete first, then hard delete after retention window.
- Add scheduled cleanup jobs.
- Add legal hold support before hard deletion.

## Access control recommendations

Role model:

- Super Admin:
  - Cross-organization emergency/admin access.
  - MFA required.
  - All actions audited.
- Admin:
  - Organization-level user and CRM administration.
  - Can view restricted fields within organization.
- Sales:
  - Can create/update CRM records in organization.
  - Can view restricted interview and pricing fields for assigned/org records.
- Read Only:
  - Can view public/internal summaries.
  - Should not view raw notes, budget/pricing fields, or sensitive objections by default.

Controls to implement:

- Organization-scoped RLS.
- `created_by`, `updated_by`, `assigned_to`, `organization_id`.
- Field-level redaction in application code.
- Separate restricted tables or views for interview raw notes and pricing context.
- Explicit export permission.

## Audit log recommendations

Create an append-only audit table:

```sql
create table public.audit_events (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid,
  actor_user_id uuid references auth.users(id),
  action text not null,
  table_name text not null,
  record_id uuid,
  field_names text[] not null default '{}',
  metadata jsonb not null default '{}',
  created_at timestamptz not null default now()
);
```

Events to log:

- Login/logout failures and successes.
- Contact create/update/delete/export.
- Interview create/update/delete/export.
- Budget/pricing field reads or exports.
- School status changes.
- Follow-up completion/deletion.
- University research runs and saves.
- Admin role changes.
- Deletion/export requests.

Do not log:

- Full raw interview notes.
- Full contact email/phone values.
- Secrets or access tokens.
- Full scraped page bodies.

## Deletion request recommendations

Support deletion for:

- Contacts by email/name.
- Interview notes tied to a contact.
- Outreach history tied to a contact.
- Follow-ups tied to a contact.

Recommended workflow:

1. Verify requester identity and authority.
2. Search records by contact identifiers.
3. Show matching record categories to an Admin.
4. Soft delete records with `deleted_at`.
5. Remove/anonymize PII fields.
6. Preserve minimal audit event.
7. Hard delete after retention window unless legal hold applies.

Recommended anonymization:

- `contacts.name = 'Deleted contact'`
- `contacts.email = null`
- `contacts.phone = null`
- `contacts.notes = null`
- redact contact references in notes where feasible.

## Export request recommendations

Support exports for:

- Contact data.
- Outreach records.
- Interview summaries and raw notes, subject to role.
- Follow-ups.
- School profile data.

Controls:

- Only Admin and Super Admin can export Restricted data.
- Sales may export assigned account data if policy allows.
- Read Only cannot export Restricted data.
- Every export must create an audit event.
- Exports should expire quickly if downloaded from storage.
- Exports should be encrypted at rest.

Recommended export format:

- JSON for complete records.
- CSV for contacts/outreach summaries.
- Separate restricted fields into a clearly labeled file.

## University-readiness assessment

The app is not yet university-ready for real stakeholder data because:

- No authentication.
- No authorization.
- No organization scoping.
- No privacy policy enforcement.
- No retention/deletion/export workflow.
- No audit logs.
- No field-level controls for restricted discovery notes and budget discussions.

The app can become university-ready if it implements:

- Institution/organization tenancy.
- Role-based access.
- RLS and backend authorization.
- Restricted data redaction.
- Data retention automation.
- Audit logs.
- Export/deletion request workflows.
- Clear AI data-use policy.

## Highest-priority recommendations

1. Add authentication and organization-scoped authorization.
2. Add role model and field-level access rules.
3. Classify raw notes, AI summaries, buyer, budget, objections, and follow-up notes as Restricted.
4. Add audit logs before real user/customer data.
5. Add retention and deletion workflows.
6. Add export request workflow with role checks.
7. Add warnings to prevent student PII or education records in notes.
8. Separate raw notes/pricing into restricted tables or views.
9. Add data processing policy for any future external AI service.
10. Add periodic privacy review and access review process.
